# 実装・検証メモ

更新日: 2026-10-23。日本語会話の成立を優先したローカル音声会話MVPです。実機受け入れのチェックは、実施結果を記録するまで合格を意味しません。

## 処理と対話方針

マイク音声を16kHz float32、512サンプルずつWebSocketへ送ります。Silero VADが発話を検出し、既定800msの無音で確定します。faster-whisper smallがbeam size 3で日本語を認識し、履歴付きでOllamaへ渡します。LLMの生成を最後まで受け取り、`final-json-v1` 形式を検証してから `reply` 本文だけをVOICEVOXへ渡し、文単位WAVを順番に再生します。

半二重方式で、生成・再生中は次の発話を処理しません。停止・新規会話は旧ターンと保留音声を破棄します。STTはスレッド内で動くため、停止操作が推論自体の即時終了を保証するわけではありません。

速度優先の0.6B / baseでは、同じ回答の繰り返しと認識品質の問題が報告されました。既定をQwen3 4B / Whisper smallへ戻し、会話方針を次のように調整しています。

- 会話の内容に答え、入力文をそのまま繰り返さない。
- 言いかけや意味が曖昧な入力は、勝手に補完せず短く確認する。
- ユーザーの訂正を受け付け、古い情報より新しい訂正を優先する。

固定フレーズへ置換して繰り返しを隠す方式ではありません。履歴はユーザー・AIの組を保ってコンテキスト予算内に収めます。調整自体は会話品質の証明ではなく、下記のテキスト・実音声チェックで検証します。

## 設定

ルートの `.env` を起動時に読みます。環境変数が `.env` より優先されます。**変更後はaivoを停止・再起動し、ブラウザを再読み込みして新規会話を開始してください。** 旧プロセスと旧履歴をそのまま使うと、設定変更の効果を比較できません。

| 環境変数 | 初期値 | 意味 |
| --- | --- | --- |
| `AIVO_STT_MODEL` | `models/whisper-small` | 事前取得済みfaster-whisperモデル |
| `AIVO_STT_DEVICE` | `auto` | CUDAを試し、利用不可ならCPU |
| `AIVO_STT_COMPUTE` | `auto` | CUDAは `int8_float16`、CPUは `int8` |
| `AIVO_OLLAMA_URL` | `http://127.0.0.1:11434` | ローカルOllama |
| `AIVO_LLM_MODEL` | `qwen3:4b` | 既存ローカルモデルを使用。未取得時のみセットアップで取得 |
| `AIVO_MAX_TOKENS` | `192` | 最大出力トークン数 |
| `AIVO_CONTEXT` | `4096` | Ollamaのコンテキスト長 |
| `AIVO_KEEP_ALIVE` | `30m` | Ollamaのモデル常駐要求 |
| `AIVO_VOICEVOX_URL` | `http://127.0.0.1:50021` | ローカルVOICEVOX Engine |
| `AIVO_SPEAKER` | `3` | VOICEVOXスタイルID、初期設定はずんだもん |
| `AIVO_VAD_THRESHOLD` | `0.5` | 発話確率しきい値、0.1〜0.95 |
| `AIVO_SILENCE_MS` | `800` | 発話確定までの無音時間、200〜3000ms |

この環境のQwen3 4BはQ4_K_Mです。Q4_K_Mは4bit中心の混合量子化であり、全テンソルINT4ではありません。Ollamaの `/api/show` で量子化を、`/api/ps` または `ollama ps` で常駐・GPU配置を確認します。STTのINT4推論は実装していません。

GPU版STTには対応するCUDA / cuDNNが必要です。不適合ならCPUへ戻るため、実行ログのデバイスも確認してください。[faster-whisperの公式手順](https://github.com/SYSTRAN/faster-whisper#gpu)を参照してください。モデル事前ロードと30分常駐要求は、メモリ不足を解消するものではありません。他プロセスを自動終了しません。

履歴は直近20往復を上限に、完全な会話の組を保ち、保守的な文字数予算で古い組から削除します。これは厳密なトークン数計算ではなく、4096トークンに20往復すべて入る保証はありません。長い会話を無制限に記憶する保証はありません。出力上限が短いと回答が途中で終わる場合があり、コンテキストを増やすとメモリや遅延が増える可能性があります。

## テキストの会話チェック

Ollamaと指定モデルを準備してから実行します。

```console
uv run python -m aivo.check_conversation
```

5ターンで、名前の提示、言いかけ、名前の訂正、会話を続ける質問、訂正後の名前の再確認を行います。回答が空、別ターンで完全に同じ回答、入力の丸写し、訂正後の名前を答えられない場合を検出します。モデル名・量子化情報・処理時間・常駐情報も出力します。

別の取得済みモデルを比較する場合:

```console
uv run python -m aivo.check_conversation --model qwen3:0.6b-q4_K_M
```

これは合成テキストによる狭い回帰チェックです。STT、TTS、音声入力、曖昧さへの対処全般、意味的に同じ回答の言い換えまで網羅しません。PASSでも一般的な会話品質や実音声動作を証明したことにはなりません。

実LLMでの今回の実行は、実行環境の `WinError 10013` により接続できず未完了です。模擬テストの通過は、実モデルの会話品質改善を証明しません。

## 音声側の切り分け

認識文とLLMの回答を分けて確認します。認識文が誤っていれば、LLMのプロンプトだけを変えても原因は解消しません。

- 実際の発話と認識文が違う: マイク選択、入力音量、雑音、STTモデルと実行デバイスを確認。
- 無発話なのに認識文が出る: スピーカー回り込みや環境音を確認し、ヘッドホンで比較。
- 認識文は正しいが同じ回答になる: 使用中モデル、旧プロセスの残存、旧会話履歴、テキスト回帰チェックを確認。
- 発話が途中で切れる: `AIVO_SILENCE_MS` を増やす。短縮は遅延と引き換えに分断を増やす可能性がある。
- 設定が変わらない: `.env` と環境変数の優先順位を確認し、aivoを再起動して新規会話を作る。

## 計測

VAD待機、STT、LLM TTFT、LLM生成、TTSを確認します。LLM生成完了と最終回答の検証を待ってからTTSを開始します。文単位の合成・再生時間と全回答の再生時間は異なり、段階時間の単純合計を初回再生遅延とはみなせません。未検証の生成途中から読み上げる方式より、初回音声までの待機時間が増える可能性があります。起動時の事前ロードとウォーム会話も分けてください。

実際の発話終端からクライアント再生開始までには転送・デコード・再生スケジューリングが含まれます。同じ時刻基準で実測し、品質も確認してからP50 / P95を評価します。最速・目標遅延達成・今回の品質改善率は未計測です。

## 最終回答の出力プロトコル

`think: false` や `/api/chat` のassistant事前入力だけでは、この環境のQwen3テンプレートで思考文の混入を止められませんでした。現在はQwen3に対して `/api/generate` の `raw: true` と明示的な会話プロンプトを使い、既存テンプレートを経由せず、空の思考区間を閉じた位置から生成します。同じ4B Q4モデルを使い、追加モデルは取得しません。

すべてのモデルで出力全体を保持し、追加キーのない `{"reply":"返答本文"}` を要求します。生成完了後に厳密に検証し、`reply` のみを画面・TTS・履歴へ渡します。JSON外の思考文、途中切れ、空本文、思考・制御タグ、不正形式はエラーにして、生の出力や定型挨拶を代わりに読み上げません。Qwen3以外も `/api/chat` で同じJSON形式を要求します。

JSONの構文検証は意味の検証ではありません。モデルが思考の説明をタグなしで正しい `reply` 内に書いた場合など、内容の自然さまで保証するものではありません。実モデルでの会話確認が必要です。

UIは `response_protocol=final-json-v1` と `runtime_id` で旧サーバーや実行の切り替わりを確認します。不一致時は開始できず、再起動を案内します。aivoを停止・再起動し、ブラウザを再読み込みして新規会話を作ってから「こんにちは」と話し、認識文・回答・読み上げに思考文やJSON自体が混ざらないことを確認してください。生成途中の読み上げは行わず、最終回答の確認を優先します。
